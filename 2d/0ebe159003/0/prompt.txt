1. Situation (The Starting Point)

The introduction begins by establishing a shared context or "opening scene" that is non-controversial. You should state facts that the reader already knows or will readily accept as true, anchoring them in a specific time and place.





Technical focus: This describes the existing stable structure or process before any problems occurred.

2. Complication (The Disturbing Event)

The complication is the "disturbing event" that creates tension by changing the stable situation. It reveals an Undesired Result (R1)—a problem that must be solved or a threat that must be addressed.





Technical focus: This could be an external shift (e.g., a new technology or competitor), an internal change (e.g., a system not working as intended), or a recently recognized performance lag.

3. Question

The complication naturally triggers a question in the reader's mind. This is the pivot upon which the entire document depends.





Technical focus: Typical questions in technical designs include: "How do we scale to meet this load?", "Which alternative architecture should we choose?", or "How do we implement this solution?".

4. Answer (The Resolution / R2)

Your Answer is the main point of the document and serves as the Desired Result (R2). It should be stated specifically and, where possible, in quantifiable terms.





Technical focus: The answer provides the solution that closes the gap between the problematic R1 and the successful R2.

Example of S-C-Q in a Technical Narrative

The sources contrast a vague, "blank" assertion with a strong S-C-Q narrative for a goal statement:





Blank Assertion (Bad): "The goal is to improve the efficiency of our API and utilize better caching".



S-C-Q Narrative (Good):





(S): "Our API currently serves 1k RPS."



(C): "Expected traffic for the Q3 launch is 10k RPS, which will exceed capacity."



(Q): (Implied) "How will we handle this load?"



(Answer/Goal): "To scale for this load, we will re-architect the load balancer to support 15k RPS".

Best Practices for Technical Introductions





Internal Logic, Not Headers: Do not use "Situation" or "Complication" as explicit section headers; let the logic drive the story flow naturally.



First 30 Seconds: The introduction should be structured so that the reader can grasp the entire thinking—the context, the problem, and the proposed solution—within the first 30 seconds of reading.



Limit to Known Truths: The introduction should remind rather than inform; do not include new data or exhibits that the reader would have to verify to accept your premise.
