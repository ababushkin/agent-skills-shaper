<title>Walking-skeleton spike: hand-produce the plan file-set + read off the contract</title>
<description>
Part 1 of the walking-skeleton spike. Parked-safe: feeds goal+KRs in as text, so it does **not** wait on the `initiative-shape` Linear-decouple.

**Why this is first.** It is the riskiest assumption and the kill gate. If a committed initiative's full hierarchy can't be expressed as cross-referenced markdown that a human reads top-down and a script can walk, the standalone-markdown premise is wrong — see the project's kill condition. Test it before building anything (eng-universal P4, Rule B2).

**Do:** by hand, take one real already-shaped initiative (this project, or another) and produce the full delivery hierarchy as a markdown file-set — deliverable → capability → node → task. **Nodes are polymorphic**: pick the format that fits the work, not always a user story — story-with-AC, capability statement, SLO, compliance obligation, migration, deprecation, experiment, and so on. Walking-skeleton task first; foundational/toolchain setup folded in, never silent. Then read the schema off the example into `docs/delivery-shape-contract.md`.

**Acceptance criteria:**

* `examples/delivery-plans/<initiative>/` exists; a human can read it top-down through all layers.
* Every node carries its **type-appropriate** completion criterion — story → AC, capability → the spec itself, SLO → numeric target, spike → decision + stop condition, migration → rollback per phase, experiment → hypothesis + success metric, KTLO → none (carve-out, roadmap A5). At least one foundational/skeleton task is present.
* `docs/delivery-shape-contract.md` names the three schema elements read off the example: directory layout · cross-reference convention (front-matter links / relative paths / manifest) · per-node tags (node `type`, deliverable↔KR, completion-criterion, task↔skeleton flag).
* The contract defines a **node-type vocabulary**: each type lists its completion-criterion form and its delegation target — SLO → Rule A4/A5, ADR → documentation-and-adrs, spike → Rule C5, incident → Rule D1, KTLO → ops slot. delivery-shape *selects and delegates*; it does not re-author these. Ground the vocabulary in the types the example actually exercises; list the rest as a to-fill appendix — **do not fabricate types the example doesn't show**.

**Constraints on the contract:**

* Use a grounded story format (Cohn / job story), not a custom "so… so…" chain.
* Distinguish external windows (notice periods, legal deadlines, soak time — allowed) from effort-in-days (forbidden, agentic P8).
* Templates stay tool-agnostic; emitted artefacts may name tools, the contract may not.

**Tests:** the "hierarchy expresses as walkable markdown" half of the kill condition.

**KR1** artefacts 1 (contract) + 2 (worked file-set). Artefact 3 (walk-script) and the mechanical-conversion proof are the gate issue (<issue id="a0c62c58-38cb-4102-bbe4-f0013234c52e">ABA-282</issue>).
</description>
