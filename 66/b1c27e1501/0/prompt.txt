# Task Shaper output written to Linear issue body for durable context

## What

After `/shape:task` runs, the enriched AC checklist and sizing decision are appended to the Linear issue body so the context survives session restarts, drain resumes, and operator inspection — not just the current session.

## Why

Without the write-back, a restarted drain or resumed session must re-run the Task Shaper from scratch, losing the analysis already done. The issue body is the durable artefact for per-ticket shaping output.

## Assumptions

* The Linear MCP's `save_issue` appends to existing body content without clobbering operator-written text.
* A delimiter marks the shaper-written section so it can be identified and not duplicated on subsequent runs.

## Key Risks

* Linear API behaviour on concurrent writes (worker session + operator editing) must be confirmed before implementing — clobbering operator edits is unacceptable.
* Idempotency: if the drain crashes and restarts, the shaper section must not be appended twice.

## Definition of Done

* After a verify-flow drain runs `/shape:task`, the Linear issue body contains the enriched AC checklist and sizing decision in a clearly delimited section.
* A second run of the shaper on the same issue does not duplicate the section.
* Operator-written content above the shaper section is unchanged.
