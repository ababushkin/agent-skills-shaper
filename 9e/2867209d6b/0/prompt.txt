7. Break each node into tasks — first task by type, feature slices, AC gate, size-check gate, dependency ordering, model routing.
Work through six sub-steps in order. Every task line ends up on a single - [ ] line in the format shown in the artefact template. The first task is not always a walking skeleton — its form depends on the node's type and on where the node's risk lives (7a). Document and maintenance nodes may carry no build tasks at all; their Completion is the artefact itself.
7a. First task by node type and risk locus — foundational work folded in. The first task's form follows the node type, the same way Completion does — a walking skeleton is a property of runnable-software nodes, not of every node:

story — the first task is the walking skeleton: the thinnest slice that runs the node's path end-to-end, marked with a leading skeleton tag — unless the node's dominant risk is core logic rather than integration. Apply the risk-locus test (parallel to the Rule A1 trigger in step 4): if the hard, uncertain part is an algorithm, a model, or a numerical method — something a thin end-to-end thread would only stub — the first task is a spike on that core, and the skeleton follows once the core is proven. A skeleton threaded through easy plumbing that mocks the actual risk surfaces nothing; it manufactures a green path (agentic P4). The skeleton's Done when: must exercise the real risky seam — the third-party call, the cross-service boundary, the unproven dependency — not a mocked stand-in for it.
spike / experiment — the node is the minimal end-to-end probe; its first task is that probe (the spike's investigation, the experiment's smallest run that yields its metric). Do not add a separate skeleton task — it is redundant with the node itself.
adr / design-doc / ktlo — no walking skeleton: these produce a document or maintain existing behaviour, not runnable software, so there is no path to run end-to-end. Tasks, if any, follow the node's Completion form; the skeleton discipline and its gate do not apply to them.

Whatever the first task is, fold its foundational setup into it. Before you write it, ask explicitly: "what toolchain or setup must exist for this task to run?" — the language, parser, scaffold, fixture, account, or environment it depends on. Fold that answer into the first task's description (a parenthetical naming the folded work is enough); never emit it as a separate setup or scaffolding task ahead of it (eng-universal Rule B2). A setup task placed before it defers the integration discovery the first task exists to surface on day one.
7b. Feature slices — each increment extends one direction and is independently deployable. After the first task, add one task per feature slice. Each slice extends the prior work in exactly one direction (one user-visible capability, one layer of the stack, one error path). A slice must be independently testable in isolation and must leave the system in a deployable state on its own — a half-wired slice that requires the next task to compile or pass is not a slice, it is a fragment. Name each slice as one observable outcome. On adr / design-doc / ktlo nodes there are no feature slices in this sense — skip 7b; their tasks follow Completion.
